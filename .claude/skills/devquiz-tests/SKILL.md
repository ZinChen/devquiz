# Составление тестов DevQuiz

Тесты живут в `tests/` как YAML-файлы и синхронизируются в базу через
`YamlSyncService`. Формально валидный тест может при этом решаться
угадыванием — ниже и требования валидатора, и правила, которых валидатор
не проверяет.

## Что где лежит

| Путь | Что это |
|---|---|
| `tests/*.yml` | сами тесты, один файл — один квиз |
| `tests/topics.yml` | словарь тем для поля `topics`, максимум 3 на вопрос |
| `app/config/tag_taxonomy.yml` | таксономия тегов; новый тег нужно разложить сюда, иначе `rake tags:sync` положит его в `unassigned` и спека упадёт |
| `app/lib/tasks/yaml_validate.rake` | валидатор, запускается в CI без базы |
| `app/services/yaml_sync_service.rb` | синхронизация YAML → база |
| `app/services/quiz_definition.rb` | какие поля вопроса доезжают до фронта |

Приложение умеет читать и личные тесты из `tests_custom/` рядом с `tests/`
(папка не трекается гитом). По умолчанию валидатор их не трогает — CI
проверяет только репозиторные. Прогнать вместе с личными:

```bash
cd app && INCLUDE_CUSTOM=1 bundle exec rake yaml_sync:validate
```

Файлы из этой папки показываются в выводе с префиксом `tests_custom/`.
Совпадение слага с репозиторным тестом — законное переопределение
(`TestSource` отдаёт custom-файл вместо оригинала), поэтому оно даёт
предупреждение, а не ошибку.

## Структура файла

```yaml
slug: postgres-locks          # уникален, совпадает с именем файла
title: "PostgreSQL: блокировки"
description: "О чём тест и что проверяет."
tags: [postgresql, locking, backend]
difficulty: advanced          # basic | advanced | expert
estimated_time: 35            # минуты

questions:
  - id: q1
    text: "Текст вопроса?"
    type: single              # single | multiple | code_challenge
    options:
      - id: a
        text: "Вариант"
        correct: false
        explanation: "Почему этот вариант не работает."
      - id: b
        text: "Вариант"
        correct: true
        explanation: "Механизм, по которому вариант верен."
    explanation: "Разбор: механизм плюс практическое следствие."
    extended_explanation: "Развёрнутая теория на 2–4 предложения."
    recommendation: "Что повторить. При наличии — ссылка на документацию."
    difficulty: medium        # easy | medium | hard
    topics: [locking, concurrency]   # максимум 3
```

`explanation` у варианта, `extended_explanation` и `recommendation`
формально опциональны для валидатора, но фактический стандарт качества
в проекте — заполнять их всегда: страница результатов показывает их в блоке
разбора, а в эталонном `tests/pg-advanced-1.yml` они закрыты на 100%
вопросов и вариантов. Это ожидаемый уровень для нового теста, не
факультативное украшение поверх минимума. Писать их сразу при черновике
вопроса, не отдельным проходом по готовому файлу — дешевле по токенам и
надёжнее, чем возвращаться и дописывать задним числом по всем вопросам:

- `explanation` на **каждый вариант**, не только у правильного — короткая
  причина, почему вариант верен или неверен, не пересказ его текста
- `explanation` вопроса — общий разбор: механизм плюс практическое следствие
- `extended_explanation` — конкретный факт сверх того, что уже сказано
  в `explanation`: команда для диагностики, число, формула, альтернатива
- `recommendation` — одна строка «что повторить», по возможности со ссылкой

Полный набор полей — в `tests/pg-advanced-1.yml`, его удобно держать как
образец.

Имя файла: `<тема>-<уровень>-<номер>.yml`, например `docker-advanced-1.yml`.

## Tags и topics — разные оси, не взаимозаменяемы

Оба поля называются похоже и оба про «темы», но отвечают на разные вопросы
и питают разные механизмы приложения. Спутать их — значит остаться без
работающей фильтрации или без работающих рекомендаций, при этом валидатор
это не поймает: оба поля синтаксически корректны в любом случае.

| | `tags` (уровень теста) | `topics` (уровень вопроса) |
|---|---|---|
| Отвечает на вопрос | «Про что этот тест в целом?» | «Какой именно навык проверяет этот вопрос?» |
| Гранулярность | крупная — весь тест целиком | мелкая — максимум 3 на вопрос |
| Источник допустимых значений | `app/config/tag_taxonomy.yml` | `tests/topics.yml` |
| Что показывает пользователю | плитки на экране выбора тем, фильтр по тестам | ничего напрямую — используется для аналитики |
| Что вычисляет приложение | похожие тесты после прохождения (пересечение тегов) | слабые места пользователя и подбор тестов, которые их закрывают |
| Где в коде | `runs_controller.rb#recommended_tests` — `tags LIKE` | `TopicIndex`, `WeakTopicsSummary`, `dashboard_controller.rb#recommended_tests` |

### Сколько topics ставить и почему не больше трёх

Одна тема — норма, две — вопрос на стыке, три — предел для вопросов, которые
без всех трёх тем теряют суть (например «добавить индекс на большую таблицу»
это разом `migrations`, `indexes` и `locking`). Лимит проверяется валидатором.

Причина лимита в том, что тема получает **полный вес** вопроса, без деления
на их число: `WeakTopicsSummary` делает `counts[topic] += wrong_count` по
каждой теме, `StrongTopicsSummary` так же засчитывает каждый верный ответ.
Значит одна ошибка в вопросе с тремя темами добавляет по баллу всем трём, а
пороги уровней в `runs_controller.rb` (`WEAK_TAG_HIGH_LEVEL = 3`,
`WEAK_TAG_MEDIUM_LEVEL = 2`) рассчитаны на то, что тем мало. Разметить вопрос
пятью темами — значит после двух ошибок подсветить десяток тем как проблемные,
то есть не посоветовать ничего.

Второй эффект — тренировки: `TopicIndex#question_ids_for` собирает вопросы по
теме, и лишняя тема тащит вопрос в тренировку, где он не по делу.

Поэтому третью тему ставят, когда она действительно часть вопроса, а не «до
кучи».

**`tags`** — крупные темы вроде `postgresql`, `kubernetes`, `ruby`. Каждый
новый тег нужно явно разложить в `tag_taxonomy.yml` — либо в `categories`
(тема, которую пользователь может выбрать как интересную), либо в `service`
(метаданные вроде источника теста, не тема). Неразложенный тег `rake
tags:sync` кладёт в `unassigned`, и спека на это падает — значит тег
потерялся молча, ни в одной плитке фильтра он не появится. Тег `self-check`
или `claude-gen` — это `source`, служебная метка, а не тема: подставлять
такие теги как если бы они описывали содержание, не нужно.

**`topics`** — узкий навык, который проверяет конкретный вопрос: `locking`,
`migrations`, `queries`. Берутся строго из словаря `tests/topics.yml` —
несловарный topic не ошибка валидатора (`TopicDictionary` покажет его как
есть, без человекочитаемого названия и цвета), но он выпадает из всей
статистики по слабым местам, потому что не входит ни в один осмысленный
раздел аналитики. Ставить `topics` на «авось» или копировать `tags`
вопроса не имеет смысла — начинают завышаться или занижаться несвязанные
темы в профиле слабых мест пользователя.

Явного поля «рекомендуемые тесты» в YAML нет — рекомендации всегда
вычисляются на лету из `tags` или `topics`, ничего руками не прописывается.
Если тест должен рекомендоваться рядом с другим — это делается только
через осмысленное пересечение тегов (не полное совпадение — хватает одного
общего), и через `topics` вопросов, реально относящихся к теме.

## Требования валидатора

- `slug` есть, уникален среди всех файлов, совпадает с именем файла —
  без него `YamlSyncService` молча пропустит файл, и тест исчезнет с сайта
- `title`, `description`, `difficulty` заполнены
- `questions` — непустой список; у каждого вопроса уникальный `id` и непустой `text`
- минимум два `options`, у каждого уникальный `id` и непустой `text`
- `type: single` → ровно один `correct: true`; `type: multiple` → хотя бы один
- уровень **не дублируется тегом**: `basic`/`advanced`/`expert`
  в `tags` запрещены. Уровень живёт только в `difficulty`, тег-дублёр даёт
  второй источник правды и врёт в фильтре

```bash
cd app && bundle exec rake yaml_sync:validate
```

## Планирование нового теста — проверка пересечений

Перед тем как писать вопросы, проверить, не покрыта ли уже тема (полностью
или частично) в существующих файлах — как в `tests/`, так и в
`tests_custom/`, если есть доступ. Без этого шага легко написать вопрос,
дублирующий по сути уже существующий под другой формулировкой, или потратить
целый блок на то, что уже закрыто одним вопросом в другом тесте.

Два уровня проверки:

1. **По полю `topics`** — самый надёжный сигнал, темы вопросов в нём узкие
   и явные:

   ```bash
   python3 -c '
   import yaml, glob
   for f in glob.glob("tests/*.yml"):
       d = yaml.safe_load(open(f, encoding="utf-8"))
       if not d or "questions" not in d:
           continue
       for q in d["questions"]:
           if "нужный_topic" in q.get("topics", []):
               print(f, q["id"], "|", q["text"][:90])
   '
   ```

2. **По ключевым словам темы** — ловит то, что `topics` не поймает (тема
   упомянута вскользь как один вопрос внутри теста на другую тему):

   ```bash
   grep -rliE 'ключевое_слово1|ключевое_слово2' tests/*.yml
   ```

   Само по себе совпадение по grep — не повод считать тему закрытой:
   единичное упоминание в дистракторе или общем тесте (`self-check-*`) не
   то же самое, что полноценный разбор. Прочитать найденные вопросы
   целиком (`text` + все `options` + `explanation`), а не полагаться на
   само совпадение.

Результат проверки определяет решение:

- **тема не встречалась** — писать as is
- **встречалась как один-два вопроса внутри смежного теста** — новый тест
  можно писать, но обходя те же формулировки и сценарии, чтобы не
  дублировать вопрос по сути под новой оболочкой
- **тема уже разобрана достаточно подробно** — не плодить содержательный
  дубль; либо выбрать более узкий фокус, либо предложить пользователю
  расширить существующий тест вместо нового файла

## Качество вопросов

### Равная длина вариантов

Самая частая и самая незаметная ошибка. Правильный ответ обрастает
уточнениями, потому что автор знает предмет и хочет объяснить, — и тест
начинает решаться по форме: решающий выбирает самый длинный вариант,
ничего не зная о теме.

```yaml
# ПЛОХО — верный ответ вдвое длиннее и единственный с обоснованием
- text: "При низкой селективности условия — когда отбирается значительная часть таблицы, последовательное чтение дешевле"
  correct: true
- text: "Когда в таблице меньше миллиона строк"

# ХОРОШО — сопоставимая длина, обоснование уехало в explanation
- text: "Когда условие отбирает значительную часть таблицы"
  correct: true
- text: "Когда в таблице меньше миллиона строк"
```

Практическое правило: обоснование через тире или точку с запятой в тексте
варианта — сигнал, что оно должно быть в `explanation`. Вариант отвечает на
«что», разбор — на «почему».

Цель не «все четыре варианта одной длины» — один дистрактор короче, другой
длиннее, это нормально и даже полезно для правдоподобия (см. ниже). Важно,
чтобы **верный ответ не выделялся на их фоне систематически**: не был ни
неизменно самым длинным, ни неизменно самым коротким по всему тесту.
Отношение длины верного к средней длине трёх неверных — не более 1.8.

Писать сразу с оглядкой на это, не откладывая на потом: сформулировав верный
вариант, прикинуть его длину относительно уже написанных или планируемых
дистракторов в том же вопросе. Дописать пояснение, ушедшее бы в вариант
ответа, сразу в `explanation`, а не в текст `text`, — тогда лишнего выравнивания
после черновика почти не требуется.

**Скобочные уточнения — тот же сигнал в миниатюре, не ловится проверкой
длины.** Верный вариант с примерами или терминами в скобках («агент ищет
файлы (grep, листинг директорий, чтение файлов)») может пройти порог 1.8
по общей длине текста и всё равно визуально выделяться на фоне сухих
дистракторов без единой скобки — форма выдаёт ответ независимо от числа
символов. Проверка: если скобка есть только у верного варианта и ни у
одного из неверных — перенести конкретизацию в `explanation` или убрать
скобку из текста вовсе, оставив факт без иллюстрации.

```yaml
# ПЛОХО — скобка есть только у верного варианта, отсеивается на глаз
- text: "Mi — двоичная единица (2^20 байт), M — десятичная (10^6 байт), это разные числа байт"
  correct: true
- text: "Это два способа написать один и тот же объём, разница только в стиле"

# ХОРОШО — конкретные числа ушли в explanation, текст варианта симметричен по форме
- text: "Mi — двоичная единица, M — десятичная, они дают разное число байт при одинаковом множителе"
  correct: true
  explanation: "Mi — это 2^20 байт, M — 10^6 байт: 750Mi ≈ 786 432 000 байт, а 750M — ровно 750 000 000 байт."
- text: "Это два способа написать один и тот же объём, разница только в стиле"
```

### Позиция правильного ответа

Не должна систематически быть первой: когда вопросы пишутся подряд, рука
сама ставит верный в `a`. На практике попытка расставлять вразнобой уже
во время написания не работает надёжно — при генерации 20 вопросов подряд
позиция `a` берёт 70–85% почти неизбежно, даже когда намеренно стараешься
её избегать. Поэтому это не рекомендация, а обязательный отдельный шаг
после черновика: сразу прогнать скрипт, который переставляет варианты
под целевое распределение (пример — в чеклисте ниже, раздел 4), а не
полагаться на память при письме.

### Равная длина: если перекос всё же остался в черновике

Правка задним числом обходится дороже, чем длина, продуманная сразу
(см. выше), но если чеклист (раздел 3) нашёл перекос — есть два пути, и
предпочтителен второй: удлинять неверные варианты правдоподобным по
существу содержанием (см. «Правдоподобные дистракторы» ниже), а не
незначащими словами ради счётчика символов, или сокращать сам текст
правильного варианта, если разбор его сути и так уже есть в `explanation`.
Обычно достаточно точечной правки 1–2 самых коротких дистракторов, а не
переписывания всего вопроса.

### Правдоподобные дистракторы

Плохой неверный вариант отсеивается без знания темы. Три источника хороших:

- **соседний термин из той же группы** — Prometheus и Grafana, Loki и
  Jaeger, pundit и devise: оба знакомы, граница размыта
- **реальное определение другого термина** — существует в природе, но
  означает не то; лучше всего отделяет знание от узнавания
- **верное утверждение, не отвечающее на вопрос** — ловит тех, кто путает
  близкие механизмы (например, ожидание блокировки и её удержание)

Избегать: вариантов из совершенно другой области, взаимоисключающих
формулировок, по которым видно, что верный среди двух похожих, и абсурда,
не опирающегося на реальную путаницу.

**Отдельный частый случай абсурда — правдоподобно звучащая выдумка.**
Дистрактор использует правильные термины темы, но описывает факт,
которого никогда не было («readiness — просто более новое название той
же пробы», «модель со временем деградирует от частого использования»,
«MCP гарантирует, что модель не будет генерировать неверные по факту
ответы»). Звучит по теме, но не с чем реально спутать — отсеивается
общими техническими знаниями или здравым смыслом, не пониманием именно
этой темы, в отличие от настоящего соседнего понятия. Тест на такой
дистрактор: можно ли представить реальный источник (документацию,
статью, чьё-то заблуждение), из которого человек мог бы вынести именно
это неверное убеждение? Если нет — переписать на реальное соседнее
понятие (Gateway API вместо несуществующего «Ingress устарел»,
fine-tuning вместо выдуманного «скилл выполняется напрямую ОС»).

### Формулировка вопроса

Писать безлично: «Нужно найти...», «Дан массив...», «Как сформулировать...» —
не «Пишете функцию...», «Реализуете...». Обращение ко второму лицу без
адресата проскакивает почти незаметно посреди файла, где остальные вопросы
безличны, и торчит как единственное исключение. Проверка при чтении черновика
целиком — вопросы должны звучать как условие задачи, а не как реплика в
диалоге с проходящим тест.

Если вопрос вводит нестандартное или не общепринятое обозначение —
рабочее название приёма, а не термин из учебника (например, `good(x)` для
предиката в бинарном поиске) — определение нужно вплести прямо в текст
вопроса при первом появлении, одной короткой фразой-приложением, без
«не X, а Y»: не отдельным абзацем и не в расчёте на то, что знающий поймёт
по контексту, а так, чтобы незнакомый с этим конкретным названием читатель
получил подсказку, а знающий её просто не заметил.

### Типы вопросов

Однотипный тест утомляет — смешивать форматы:

| Формат | Что проверяет |
|---|---|
| Определение | знание термина, разминка |
| Разница между X и Y | понимание границы |
| Лишний в ряду | классификацию |
| Сценарий-ловушка | понимание механизма |
| Диагностика по симптому | опыт эксплуатации |

Сценарные вопросы ценнее определений: они отличают тех, кто делал, от тех,
кто читал.

### Сложность

- `easy` — знает любой, кто работал с темой; проверка словаря
- `medium` — требует понимания механизма, а не запоминания
- `hard` — граничные случаи, неочевидные следствия, диагностика

На 20 вопросов разумно примерно 5 / 10 / 5. Тест целиком из `hard`
демотивирует, целиком из `easy` не даёт информации.

### Число вопросов

Общее число вопросов в тесте должно быть кратно 5 (10, 15, 20, 25...).
Планируя объём заранее — округлять до ближайшего кратного 5, а не
останавливаться на произвольном числе вроде 11 или 13.

### Чего не должно быть

- **устаревающего** — «какая модель сейчас SOTA», «сколько параметров у X»
- **версионно-зависимого без версии** — если ответ зависит от Rails 7
  против Rails 8, зафиксировать версию в `description`
- **спорного по существу** — формулировать через «что обычно понимают
  под…», в пояснении отмечать, что практика плавает
- **внутренней специфики** — имена коллег, внутренние домены, номера
  тикетов; если тест вырос из рабочих заметок, вычистить перед коммитом

## Стиль пояснений

`explanation` вопроса — механизм и практическое следствие, а не пересказ
формулировки верного варианта. `recommendation` — одна строка «что
повторить», по возможности со ссылкой на документацию.

**`recommendation` — учебная рекомендация, не совет по написанию кода.**
Она отвечает на вопрос «что изучить, чтобы такие задачи решались
уверенно» — тему, концепцию, источник, — а не «как правильно оформить
реализацию» или «что проверить перед коммитом». Формулировка вроде «явно
выписывать сигнатуру функции без лишних параметров перед реализацией» —
совет разработчику по кодстайлу, он не подсказывает, что почитать или
прорешать, и не годится сюда.

```yaml
# ПЛОХО — совет по написанию кода, а не по обучению
recommendation: "Явно выписывать сигнатуру good(x) без параметров L/R перед тем, как приступать к реализации цикла поиска."

# ХОРОШО — что повторить, со ссылкой
recommendation: "Повторить паттерн «бинарный поиск по предикату» (binary search on answer) — разбор шаблона и типичных ошибок реализации."
```

Не начинать каждую рекомендацию файла с одного и того же глагола
(«Повторить...», «Прорешать...») — та же ошибка шаблонности, что с «Верно:»
и «X, а не Y» у пояснений вариантов, только на уровне целого файла: разово
незаметно, но на 15-20 вопросах подряд бросается в глаза. Разнообразить
зачин: иногда назвать тему/алгоритм прямо («Алгоритм Дейкстры стоит
разобрать через призму BFS...»), иногда сформулировать через следствие
(«Оценка памяти стека рекурсии — O(h)... стоит держать в голове отдельно
от времени»), иногда — всё же «Повторить»/«Прорешать», если это правда
самая естественная формулировка для конкретного вопроса. Проверять `grep
-c '^\s*recommendation: "Повторить' файл.yml` при массовой правке
рекомендаций — если больше 3-4 на 15-20 вопросов, часть переформулировать.

### Блок кода в extended_explanation — когда вопрос про конкретную механику

Если суть вопроса — не выбор паттерна по формулировке условия, а конкретная
последовательность операций (шаблон цикла бинарного поиска, снятие/добавление
в монотонном стеке, dummy-узел при слиянии списков, алгоритм Кана через
индегри), короткий блок кода в `extended_explanation` фиксирует механику
нагляднее, чем то же самое прозой. Признак, что вопрос — подходящий кандидат:
явное наличие итерации, состояния, меняющегося по шагам (`L`, `R`, стек,
очередь, накопленная сумма), а не абстрактное «какой паттерн выбрать».

Формат — 5–12 строк **псевдокода**, не кода на конкретном языке: тест про
алгоритмы, а не про синтаксис, и не весь проходящий тест обязан знать Ruby
или Python. Комментарии — только на ключевых строчках, где неочевидно,
почему шаг важен, а не построчный пересказ. Оборачивать в тройные кавычки
(fenced code block), они добавляются в конец `extended_explanation` через
пустую строку после прозы:

```yaml
extended_explanation: |
  Порядок сортировки точек при равенстве координат критичен: если
  бронь A заканчивается ровно в момент начала брони B, комната
  должна успеть освободиться — поэтому точка конца обрабатывается
  раньше точки начала при одинаковом времени.

  ```
  points = []
  for (start, end) in bookings:
      points.push((start, +1))
      points.push((end,   -1))
  sort points by (time, type)   // при равенстве -1 раньше +1

  current, peak = 0, 0
  for (time, type) in points:
      current += type
      peak = max(peak, current)
  ```
```

Не на каждый вопрос теста — только там, где код действительно проясняет
механику. Вопросы про выбор между двумя паттернами по формулировке условия
(«какая структура данных решает задачу за O(n)») от кода не выигрывают —
там ответ в распознавании сигнала в тексте, а не в деталях цикла.

### Extended_explanation — не парафраз explanation

Самая частая ошибка при первом черновике: `extended_explanation` говорит
то же самое, что уже сказано в `explanation`, другими словами. Читатель,
дошедший до второго поля, узнаёт не больше, чем из первого — поле не
оправдывает своё существование.

Проверка на этапе написания: закрыть `explanation` и спросить — есть ли
в `extended_explanation` факт, которого там не было? Годятся: конкретная
команда или API для диагностики, число или формула, альтернативный
инструмент/подход, смежный кейс того же принципа, важная оговорка или
ограничение метода из `explanation`.

```yaml
# ПЛОХО — то же самое другими словами
explanation: "Сессионный advisory lock снимается явным вызовом или обрывом сессии. В transaction pooling соединение возвращается в пул и достаётся другому клиенту вместе с висящей блокировкой."
extended_explanation: "pg_advisory_lock живёт в рамках сессии PostgreSQL. PgBouncer в transaction pooling держит соединение только на время транзакции, отдавая его в пул вместе с локом."

# ХОРОШО — новый факт: как проверить и чем закрыть по-другому
extended_explanation: "Проверить, использует ли код обычный лок: `SELECT * FROM pg_locks WHERE locktype = 'advisory'`. Альтернатива `pg_advisory_xact_lock` — вообще не держать advisory-лок в transaction pooling, а блокировать строку через `SELECT ... FOR UPDATE` внутри транзакции."
```

### Пояснения к вариантам ответа

Короткая строка на вариант, одно-два предложения. Писать сразу вместе с
самим вариантом, а не отдельным проходом после черновика — причина ещё
свежа в голове на этом этапе, а не придумывается заново постфактум по
голому тексту варианта.

**Не пересказывать текст варианта другими словами.** Та же ошибка, что и
с `extended_explanation`, но чаще у правильного ответа: пояснение почти
дословно повторяет формулировку варианта, добавляя союз или меняя порядок
слов. Пояснение должно объяснять механизм или причину, а не подтверждать
факт, который уже виден в тексте варианта.

```yaml
# ПЛОХО — то же самое другими словами
text: "dbt выполняет трансформации внутри хранилища и строит граф моделей"
explanation: "dbt выполняет трансформации внутри хранилища и строит граф моделей через ref()."

# ХОРОШО — новая причина
text: "dbt выполняет трансформации внутри хранилища и строит граф моделей"
explanation: "Своего планировщика у dbt нет — он выполняется по требованию или из-под внешнего оркестратора вроде Airflow."
```

**Не начинать с «Верно:» у правильного ответа** — маркер избыточен,
интерфейс и так показывает, какой вариант верный.

```yaml
# ПЛОХО
explanation: "Верно: HPA меняет число реплик по CPU, памяти или метрикам."
# ХОРОШО
explanation: "HPA управляет числом реплик, ориентируясь на CPU, память или собственные метрики приложения."
```

**Избегать шаблонного противопоставления «X, а не Y».** У неверного
варианта объяснять утвердительно — чем названная вещь является на самом
деле, — вместо отрицания формулировки варианта. Конструкции «это X, а не
Y», «не X, а Y», «Наоборот: …» на дистанции читаются однообразно. Ловушка
та же, что с позицией `a`: объясняя неверный вариант, проще всего сказать
«на самом деле верно X, а не то, что здесь» — естественная формулировка на
одном вопросе, которая от этого не перестаёт незаметно повторяться на всём
файле, если писать её так на каждом. Проверять `grep` из чеклиста (раздел 5)
сразу по мере написания, не дожидаясь последнего вопроса.

```yaml
# ПЛОХО
explanation: "Синхронизация схем — задача Schema Registry, а не MirrorMaker."
explanation: "Алертинг по латентности строится на метриках, а не на самой трассировке."
# ХОРОШО
explanation: "Схемами занимается Schema Registry со своими механизмами совместимости."
explanation: "Оповещения по времени ответа строят на метриках."
```

Противопоставление уместно там, где несёт содержание, а не заполняет
форму: «Так выглядит FORWARD-совместимость: старый код читает данные новой
схемы» объясняет, чем вариант является, попутно разводя два термина.

### Тон

Ирония в пояснениях уместна и сохраняется осознанно — живая формулировка
запоминается лучше сухой и точнее передаёт, почему что-то на практике
оборачивается проблемой:

> «Ошибки при этом не будет, что и делает проблему коварной: настройка
> выглядит применённой, а эффекта нет.»

Граница простая: ирония направлена на ситуацию или типичную ошибку, а не
на того, кто проходит тест. При последующих проходах по файлу её не
вычищать.

Шуточные варианты ответа (формально корректная расшифровка аббревиатуры с
абсурдным смыслом) — не больше одного на вопрос и не короче остальных,
иначе отсеиваются на глаз и вопрос из четырёх вариантов превращается в
вопрос из трёх.

## Чеклист перед коммитом

Прогонять сразу после первого черновика — как последний шаг самой задачи,
не дожидаясь отдельной просьбы проверить. Позиция правильного ответа,
перекос длины и шаблонные формулировки почти гарантированно всплывают при
первом же прогоне; находить их отдельным заходом позже — двойная работа.

```bash
# 1. Формальная валидация (INCLUDE_CUSTOM=1 — вместе с tests_custom/)
cd app && bundle exec rake yaml_sync:validate

# 2. Ровно один correct, четыре варианта, непустой explanation — вопроса
#    и каждого варианта, extended_explanation и recommendation на вопрос
ruby -ryaml -e '
YAML.load_file(ARGV[0])["questions"].each do |q|
  c = q["options"].count { |o| o["correct"] }
  puts "#{q["id"]}: correct=#{c}" unless c == 1
  puts "#{q["id"]}: options=#{q["options"].size}" unless q["options"].size == 4
  puts "#{q["id"]}: explanation мал" if q["explanation"].to_s.size < 80
  puts "#{q["id"]}: нет extended_explanation" if q["extended_explanation"].to_s.empty?
  puts "#{q["id"]}: нет recommendation" if q["recommendation"].to_s.empty?
  q["options"].each do |o|
    puts "#{q["id"]}/#{o["id"]}: нет explanation варианта" if o["explanation"].to_s.empty?
  end
end' tests/файл.yml

# 3. Отношение длины верного к средней длине неверных — не должно быть > 1.8
#    ни в одну, ни в другую сторону (верный не должен выделяться на фоне
#    дистракторов; сами дистракторы друг с другом выравнивать не нужно)
ruby -ryaml -e '
YAML.load_file(ARGV[0])["questions"].each do |q|
  c = q["options"].find { |o| o["correct"] }
  w = q["options"].reject { |o| o["correct"] }
  r = c["text"].size.to_f / (w.map { |o| o["text"].size }.sum.to_f / w.size)
  puts "#{q["id"]}: #{r.round(2)}" if r > 1.8 || r < 1.0 / 1.8
end' tests/файл.yml

# 3а. Скобка есть только у верного варианта — асимметрия, не ловится
#     проверкой длины
ruby -ryaml -e '
YAML.load_file(ARGV[0])["questions"].each do |q|
  c = q["options"].find { |o| o["correct"] }
  w = q["options"].reject { |o| o["correct"] }
  puts "#{q["id"]}: скобка только у верного" if c["text"].to_s.include?("(") &&
    !w.any? { |o| o["text"].to_s.include?("(") }
end' tests/файл.yml

# 4. Распределение позиций верного ответа — без перекоса в a
ruby -ryaml -e '
t = Hash.new(0); n = 0
YAML.load_file(ARGV[0])["questions"].each do |q|
  t[q["options"].index { |o| o["correct"] }] += 1; n += 1
end
puts t.sort.map { |k, v| "#{%w[a b c d e][k]}=#{(100.0 * v / n).round}%" }.join("  ")' tests/файл.yml

# 5. Стилевые шаблоны в пояснениях к вариантам — должно быть пусто
grep -nE '^\s+explanation: "(Верно|Наоборот)' tests/файл.yml
grep -nE '^\s{8}explanation:.*, а не ' tests/файл.yml

# 5а. Пояснение варианта пересказывает его текст — порог 0.6 ловит
#     почти дословные повторы, разница только в порядке слов или союзе
python3 -c '
import yaml, difflib
d = yaml.safe_load(open("tests/файл.yml", encoding="utf-8"))
for q in d["questions"]:
    for o in q.get("options", []):
        t, e = o.get("text", "").lower(), o.get("explanation", "").lower()
        if not e:
            continue
        r = difflib.SequenceMatcher(None, t, e).ratio()
        if r > 0.6:
            qid, oid = q["id"], o["id"]
            print(f"{qid}/{oid} ratio={r:.2f}")
'

# 6. Внутренняя специфика — имена, домены, номера тикетов
```

## Массовые правки

Файлы теста большие (600+ строк), и правки обычно затрагивают все вопросы
сразу. Как только правка касается больше 4–5 мест в файле — не редактировать
построчно, а сразу писать разовый скрипт со словарём «старый текст → новый»,
прогонять по файлу и проверять результат через `YAML.safe_load`. Построчная
правка такого объёма стоит заметно дороже одного скрипта и не даёт
преимущества в надёжности. Так же сохраняются комментарии-разделители
секций и стиль кавычек, которые переформатировал бы полный цикл load/dump.
